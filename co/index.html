แนวทางย้ายโดเมนจาก .thailandpost.com เป็น .thailandpost.co.th

1. ภาพรวม Concept

โจทย์คือระบบเดิมใช้โดเมนกลุ่ม .thailandpost.com และต้องย้ายหรือเพิ่มบริการใหม่มาอยู่ใต้ .thailandpost.co.th

Reference: Administrator Technical Manual - THP

สภาพแวดล้อมเดิม

จากเอกสารเดิม ระบบ NAM มีองค์ประกอบหลักคือ Load Balancer, Identity Server, Access Gateway, Reverse Proxy Application, SAML/OIDC และ MFA/AA โดย Access Gateway ทำหน้าที่เผยแพร่ URL, กำหนด Protected Resource / Policy และบางระบบมี Header Injection

Load Balancer เดิม Identity Server / IDP เดิม Access Gateway เดิม Reverse Proxy Applications

ประเด็นหลักของการเปลี่ยนโดเมน

Reverse Proxy แต่ละชุดจะมี Cookie Domain ของตัวเอง เช่น .thailandpost.com หรือ .thailandpost.co.th ดังนั้นถ้าจะใช้ Domain-Based Multi-Homing คนละ root domain ควรแยก Reverse Proxy หรือแยก Access Gateway เพื่อไม่ให้ Cookie Domain ชนกัน

ใจความสำคัญ: Cookie ของ .com กับ .co.th แชร์กันตรง ๆ ไม่ได้ แต่สามารถทำ SSO ได้ผ่าน Identity Server / IDP เดียวกัน

2. SSO ระหว่าง .com และ .co.th ทำงานยังไง

IDP เป็นจุด Login กลาง ส่วน Reverse Proxy แต่ละตัวเป็นจุดรับ Traffic และสร้าง Session Cookie ตามโดเมนของตัวเอง

กรณี User เข้า .com ก่อน

  1. User เข้า URL เดิม เช่น wlsm.thailandpost.com
  2. Reverse Proxy เดิมตรวจสอบ Session ของ .thailandpost.com
  3. ถ้ายังไม่มี Session จะ Redirect ไป Identity Server / IDP เดิม
  4. User Login สำเร็จ และ IDP สร้าง Session ของ IDP
  5. Reverse Proxy เดิม Set Cookie ภายใต้ .thailandpost.com

กรณี User ต่อมาเข้า .co.th

  1. User เข้า URL ใหม่ เช่น praiai.thailandpost.co.th
  2. Reverse Proxy ใหม่ตรวจสอบ Session ของ .thailandpost.co.th
  3. ถ้ายังไม่มี Session จะ Redirect ไป IDP เดิม
  4. IDP เห็นว่า Browser นี้มี IDP Session อยู่แล้ว จึงไม่ถามรหัสซ้ำ
  5. Reverse Proxy ใหม่ Set Cookie ภายใต้ .thailandpost.co.th
สรุป: SSO ข้ามโดเมนไม่ได้เกิดจากการแชร์ Reverse Proxy Cookie ระหว่าง .com กับ .co.th แต่เกิดจากการใช้ Identity Server / IDP เดียวกันเป็นศูนย์กลาง Login หาก IDP URL เดิมยังใช้งานอยู่ ผู้ใช้ที่มี IDP Session แล้วจะถูก Redirect กลับเข้าโดเมนปลายทางได้โดยไม่ต้อง Login ซ้ำ

Solution 1

สร้าง Reverse Proxy ใหม่สำหรับ .co.th บน Access Gateway Cluster เดิม

1

แนวทางนี้ใช้ Access Gateway Cluster เดิมที่มีอยู่ แล้วเพิ่ม Reverse Proxy ใหม่สำหรับโดเมน .thailandpost.co.th โดยกำหนด Cookie Domain เป็น .thailandpost.co.th แยกจาก Reverse Proxy เดิมที่ใช้ .thailandpost.com

Concept การทำงาน

  • DNS ของ praiai.thailandpost.co.th ชี้เข้า Load Balancer / VIP เดิม
  • Access Gateway Cluster เดิมรับ Traffic แล้ว Match กับ Reverse Proxy ใหม่สำหรับ .co.th
  • ถ้า User ยังไม่มี Session ของ .co.th จะ Redirect ไป Identity Server / IDP เดิม
  • หลัง Login สำเร็จ IDP Redirect กลับมายัง URL เดิมที่ User เรียก
  • Access Gateway Set Cookie ภายใต้ .thailandpost.co.th แล้ว Forward ไป Backend

ค่าที่ต้องเตรียม / ตั้งค่า

Reverse Proxy ใหม่
  • Cookie Domain: .thailandpost.co.th
  • Published DNS: praiai.thailandpost.co.th
  • Proxy Service: PraiAI
  • Multi-Homing: Domain-Based
  • Host Header: Forward Received Host Name หรือ praiai.thailandpost.co.th
Backend / Network
  • Backend: 10.253.52.107
  • Protocol: HTTP
  • Port: 80
  • Certificate ต้องครอบคลุม praiai.thailandpost.co.th
  • Protected Resource / Policy ใช้ตาม Requirement

จุดเด่น

  • ทำได้เร็วกว่า เพราะไม่ต้องลง Server เพิ่ม
  • ใช้ Load Balancer / Access Gateway Cluster เดิมได้
  • ประหยัด Infra และลดงาน Operation
  • เหมาะกับการ Migration แบบค่อยเป็นค่อยไป
  • ยังใช้ IDP / MFA / Policy เดิมร่วมกันได้

ข้อควรระวัง

  • ยังอยู่บน AG Cluster เดิมร่วมกับระบบ .com ดังนั้นการ Apply Change ต้องระวังผลกระทบกับบริการเดิม
  • Capacity ของ AG เดิมต้องรองรับ Traffic เพิ่ม
  • ต้องจัดการ Certificate และ DNS ของ .co.th ให้ถูกต้อง
Solution 2

ติดตั้ง Access Gateway Server / Cluster ใหม่สำหรับ .co.th

2

แนวทางนี้แยก Access Gateway Cluster ใหม่เพื่อรองรับโดเมน .thailandpost.co.th โดยเฉพาะ ส่วน Identity Server / IDP เดิมยังสามารถใช้ร่วมกันได้ ทำให้แยก Traffic, Change Window, Certificate, Monitoring และ Operation จากระบบ .com เดิมได้ชัดเจนกว่า

Concept การทำงาน

  • DNS ของ praiai.thailandpost.co.th ชี้เข้า VIP / Load Balancer ใหม่ หรือ Pool ใหม่
  • Access Gateway Cluster ใหม่รับ Traffic ของ .co.th โดยเฉพาะ
  • AG ใหม่ผูกกับ Identity Server / IDP เดิมเพื่อใช้งาน Login / MFA / Policy เดิม
  • หลัง Login สำเร็จ IDP Redirect กลับมายัง AG ใหม่
  • AG ใหม่ Set Cookie ภายใต้ .thailandpost.co.th แล้ว Forward ไป Backend

ค่าที่ต้องเตรียม / ตั้งค่า

Infrastructure ใหม่
  • ติดตั้ง Access Gateway Server / Cluster ใหม่
  • Register AG ใหม่เข้ากับ NAM Admin Console
  • ผูก AG ใหม่กับ Identity Server Cluster เดิม
  • ตั้งค่า Load Balancer / VIP / DNS ใหม่
  • เปิด Firewall ระหว่าง User, LB, AG, IDP และ Backend
Reverse Proxy ใหม่
  • Cookie Domain: .thailandpost.co.th
  • Published DNS: praiai.thailandpost.co.th
  • Proxy Service: PraiAI
  • Backend: 10.253.52.107:80
  • Protocol to Backend: HTTP

จุดเด่น

  • แยกจากระบบ .com เดิมชัดเจน
  • ลดความเสี่ยงจากการ Apply Change กระทบระบบเดิม
  • เหมาะกับ Production ระยะยาว
  • แยก Monitoring / Log / Operation ได้ง่ายกว่า
  • รองรับการขยายระบบ .co.th เพิ่มเติมในอนาคตได้ดี

ข้อควรพิจารณา

  • ต้องใช้ Server / Resource / IP / VIP / Certificate เพิ่ม
  • ใช้เวลา Implement และ Test มากกว่า Solution 1
  • มีภาระ Operation เพิ่ม เช่น Patch, Backup, Monitoring, DR และ Capacity Planning

5. Recommendation / Talking Point

เอาไว้ใช้คุย Concept กับลูกค้าแบบสั้นและชัด

ถ้าเป้าหมายคือย้ายโดเมนให้เร็ว

แนะนำเริ่มที่ Solution 1

สร้าง Reverse Proxy ใหม่สำหรับ .co.th บน Access Gateway Cluster เดิมก่อน เพื่อทดสอบ Flow, Cookie Domain, Host Header, Backend และ Policy โดยไม่ต้องลงทุน Infra ใหม่ทันที

เหมาะกับ: Pilot, PoC, Migration ระยะสั้น, บริการที่ Traffic ไม่สูงมาก และต้องการลดระยะเวลาทำงาน

ถ้าเป้าหมายคือใช้ .co.th เป็น Main Domain ระยะยาว

พิจารณา Solution 2

ติดตั้ง Access Gateway Cluster ใหม่เพื่อแยกระบบ .co.th ออกจาก .com ชัดเจน ลดความเสี่ยงกระทบระบบเดิม และทำให้ Operation / Monitoring / Change Management แยกกันได้

เหมาะกับ: Production ระยะยาว, ต้องการแยก Risk, ต้องการรองรับหลายบริการ .co.th ในอนาคต

คำถามที่ควร Confirm ก่อนออกแบบจริง

  • IDP URL ปัจจุบันอยู่ใต้ .com หรือไม่ และมีแผนย้ายเป็น .co.th ด้วยหรือเปล่า
  • ต้องให้ SSO ระหว่าง .com และ .co.th ทำงานต่อช่วง Migration นานเท่าไร
  • จะเปิด .com เป็น Redirect ไป .co.th หรือจะปิดทันทีหลัง Cutover
  • Certificate ที่ใช้รองรับ Wildcard หรือ SAN ของ .co.th แล้วหรือยัง
  • Load Balancer / VIP เดิมรองรับการเพิ่มโดเมน .co.th หรือควรแยก VIP ใหม่
  • Backend ต้องการ Host Header เป็น IP, ชื่อ backend, หรือ Published DNS
  • Protected Resource / Policy / MFA ต้องเหมือนของเดิมหรือมีเงื่อนไขใหม่
  • ต้องการแยก Log / Monitoring / SLA ระหว่าง .com และ .co.th หรือไม่
